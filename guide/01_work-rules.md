# 01 작업 규칙 — 승인·생성·수정·보고

`00_project-instructions.md`의 열두 가지를 실제로 적용하는 법. 각 규칙 끝의 `E-NN`은 근거가 된 실제 사건(`07_error-registry.md`)이다.

---

## 1. 사용자 말 → Claude 행동 해석표

애매하면 이 표를 따른다. 표에 없으면 **더 적게 하는 쪽**을 고르고 묻는다.

| 사용자가 한 말 | Claude가 할 일 | 하지 않을 일 |
|---|---|---|
| "프롬프트 만들어 / 써 봐 / 금지할 거 다 넣어서 만들어" | 위험 목록 + 프롬프트 전문을 보여 주고 멈춘다 | 생성 (E-02) |
| "만들어 / 생성해 / 뽑아" (이미지·영상) | 프롬프트를 먼저 보이고 한 장(한 개)만 생성 → 검수 보고 | 여러 장 연속 생성, 해상도 임의 상향 (E-08) |
| "작성해서 만들어" | 작성 → 위험 목록 → 1회 생성 → 보고 | 승인 없이 2회째 |
| "이상해 / 연관성이 없어 / 실제와 다르지 않아?" (지적·질문) | 원인 분석 + 수정안 2~3개 + 질문 하나 | 묻지 않고 재생성 (E-01) |
| "디테일만 올려 / 하늘만 바꿔" | 그것만 바꾸고 나머지를 보존 목록에 적는다 | 밝기·개수·구도까지 손대기 (E-04) |
| "4k로 / 1080p로" | 그 해상도로 생성 | 업스케일 등 다른 방식으로 대체 (E-03) |
| "픽스 / 확정 / 이걸로 / 이대로" | 정본 문서에 ID·날짜·한계와 함께 기록 | 확정본 재생성, 확정본 자동 개선 |
| "진행 / 해" | 직전에 제안한 범위 그대로 실행 | 범위 확대 |
| "임시 픽스" | 확정과 같게 기록하되 "임시"와 남은 문제 표시 | — |
| 사진 첨부(모니터를 찍은 사진) | 모양·색·밝기 비교 기준으로만 쓰고 원본 파일을 요청 | 생성 참조로 직접 사용 (E-21) |
| "전에 정했잖아 / 다 보고 가져와" | `decisions.md`·Higgsfield 저장본을 직접 찾아 확인 | 되묻기 (E-10) |

## 2. 생성 전 — 네 단계

1. **확인**: 정본에서 쓸 참조의 현재 이미지와 ID를 연다. 문서에 적힌 주소만 믿지 않는다(E-11).
2. **위험 목록**: 이 생성에서 잘못될 수 있는 것을 3~6개 꼽는다. 흔한 것: 첫 프레임이 빔, 좌우 뒤집힘, 시선 반전, 렌즈 표류, 소품이 다른 손·다른 크기·다른 탁자로 감(E-17), 참조 사진의 얼굴·색이 섞임(E-16), 금지어가 오히려 불러옴(E-27).
3. **막는 문장**: 위험마다 한 줄. 긴 금지 목록보다 필요한 자리의 짧은 잠금이 잘 듣는다.
4. **보이기**: 위험 목록 + 프롬프트 전문 + 설정(모델·해상도·길이·참조 역할)을 보이고, 생성 지시가 있었으면 그때 생성한다.

## 3. 생성 후 — 보고 형식

```
만든 것: [모델] [job ID] [해상도·길이]
맞은 것: [지시 항목별 ✔]
미달:   [항목 — 측정값 또는 눈으로 본 것]
판단:   [쓸 수 있음 / 고칠 것 하나 / 방식 변경 필요]
다음:   [선택지 2~3개] — 질문 하나
```

- 측정할 수 있는 것은 숫자로(밝기, 위치 %, 크기, 구조 일치도 — `06_qa-and-cost.md`). 측정하지 않았으면 "추정"이라고 쓴다(E-24).
- 이전 보고가 틀렸으면 이번 보고 첫 줄에 정정한다.
- 결과물은 프로젝트의 정해진 폴더에 넣는다(E-30).

## 4. 고칠 때

- **한 번에 한 가지.** 실패했을 때 무엇이 효과였는지 가릴 수 있어야 한다(E-05). 예외는 떼면 성립하지 않는 두 변경뿐(켠 화면과 그 화면 빛).
- **확정 프롬프트에서 출발한다.** 새로 쓰지 않고 바뀐 줄만 고친다. 확정본의 카메라·동작 문장을 바꾸면 결과가 통째로 달라진다(E-06).
- **2회 규칙.** 같은 이미지·같은 실패에 2번 시도해 안 되면 멈춘다. 대안: 샷을 쪼갠다 / 사건을 줄인다 / 개념을 단순화한다 / 모델이 아니라 직접 편집(합성)한다 / 후반 작업으로 넘긴다(E-07, E-23).
- **원인을 먼저 쓴다.** "다시 해 보겠습니다"가 아니라 "원인: … 그래서 …를 바꾼다".

## 5. 확정과 기록

- 확정되면 `decisions.md`에 한 줄 규칙 + 날짜 + 근거, `asset-registry.md`에 ID·태그·확정 job·알려진 한계를 적는다.
- 확정본은 지우지도 재생성하지도 않는다. 파생은 항상 확정본에서 갈라낸다.
- 사용자가 결정을 번복하면 옛 줄을 지우지 말고 "폐기(날짜·이유)"로 남기고 새 줄을 위에 쓴다.

## 6. 질문하는 법

- 처음에 한 번, 필요한 것을 모아서 묻는다(`templates/decisions.md`의 "시작 전에 물어볼 것").
- 이후 질문은 답변 끝에 하나. 같은 질문을 표현만 바꿔 반복하지 않는다.
- 내가 기본값을 가정했으면 질문 대신 "기본값 X로 진행, 다르면 알려 달라"로 쓴다(진행을 막지 않는 경우만).
